# 행사 플랫폼 현황 분석 및 제품 방향 재정립안

작성일: 2026-11-04, Asia/Seoul

검토 기준: GitHub `main` 및 로컬 동일 커밋 `0bfc2939ec2539e7ebe244e365305188a8613c75`, 공개 Render 테스트 앱, 기존 기능 명세와 작업 기록.

사용자가 이번 검토에서 선택한 방향은 **청소년 외 다양한 행사까지 포괄하는 서비스**다. 이 방향은 확정 사항으로 반영한다. 아래 우선순위·화면 개편·운영 방식은 현재 구현을 바탕으로 한 제안이며, 기존 기능을 임의로 폐기하거나 제품명을 확정하는 문서가 아니다.

후속 합의: 콘텐츠 수정·행사 준비부터 개선하며, 안내 수정·변경 이력·공개 미션 조건 보호와 필수 누락 공개 차단/선택 기능 경고를 적용한다. 아래 현황은 최초 분석 시점이며 최신 처리 결과는 [기능 점검·개선 결과](feature-audit-2026-11-04.md)를 따른다.

## 1. 제품에 대한 결론

**여러 종류의 행사에서 참가자의 안내·참여와 주최 측의 현장 운영·결과 정리를 연결하는 웹 플랫폼**으로 정의한다.

현재 앱은 화면 시안 단계를 넘어 실제 저장·인증·권한·집계가 동작하는 개발 버전이다. 행사·부스·참여·설문·소통 기능의 범위는 넓지만, 여러 행사에 반복 제공하는 제품으로서의 설정 체계와 운영 기반은 더 필요하다. 현 단계의 핵심 과제는 행사별 적용과 운영 완성도다.

주된 도입자는 행사 주최기관·운영사이며, 사용자는 참가자·부스 담당자·운영본부·플랫폼 운영자다. 참가자 편의와 운영 업무 감소를 함께 검증해야 한다.

## 2. 실제로 확인한 상태

### 2.1 최신 코드와 공개 사이트는 다른 버전

- 최신 코드 마지막 커밋은 2026-10-20의 문구·영어·날씨 설정 개선이다.
- 2026-11-04에 공개 사이트의 홈·프로그램·미션·안전·내 참여 화면을 모바일 크기로 직접 열었다. 확인한 5개 화면에서 가로 넘침은 없었다.
- 공개 사이트의 `app.js`는 저장소의 `257aabf` 및 `a8d83e2` 시점 파일과 바이트 단위로 일치했다. 두 커밋이 동일 파일을 포함하므로 이것만으로 서버 전체의 배포 커밋을 확정하지는 않는다.
- 공개 행사 API에는 최신 코드의 `key_visual`, `header_name`, `show_sample_notice` 항목이 없었다. 공개 화면에서 최신 개선 전체를 평가하면 구현 상태를 과소평가할 수 있다.
- 공개 API 기준 샘플 데이터는 존 3개, 부스 4개, 프로그램 2개다. 평면도·보행 지점·보행 경로는 비어 있고 현장 안전 연락처도 미설정이다.
- `/api/status`에서 번역·날씨는 `not_configured`, 상품권은 `manual_export`다. 공개 안전 화면에서도 날씨 미설정과 앱 신고 비활성 상태를 확인했다.
- 샘플 날짜는 개발용이다. 공개된 날짜를 실제 행사 일정으로 해석하지 않는다.

## 4. 확장 방향을 결정하는 핵심 발견

### A. 다중 행사 참여 오류 — 가장 먼저 수정

임시 환경에서 같은 참가자 쿠키로 행사 A의 패스를 만든 뒤 행사 B에 패스를 만들면, A는 HTTP 200, B는 HTTP 409와 ‘중복되거나 연결된 정보가 올바르지 않습니다.’를 반환했다.

`participants.token`은 전체 테이블에서 고유한데, 패스 조회·생성은 행사별로 수행하면서 같은 쿠키 토큰을 재사용한다. 여러 행사를 운영하는 서비스의 기본 이용 흐름을 막는 문제다.

제안: 기기 연결 식별자와 행사별 참가 기록의 관계를 명확히 설계하고, A→B→A 이동·재접속·동시 요청을 검증한다. 기존의 비회원 참여·복구 기능 제외 결정은 유지한다. 이 결함을 고치기 위해 회원가입을 도입할 필요는 없다.

### B. 행사별 기능 선택이 실제 제품 기능으로 완성되지 않음

현재 설정에 `features` 값은 있으나 프로그램·미션·설문을 끄는 저장 및 화면 연결이 없다. 설정 API에 false를 보내도 기본값 true가 유지되고 참가자 메뉴도 고정이다.

제안: 설정 저장, 메뉴·홈 카드, 직접 링크/API 동작까지 같은 규칙을 적용한다. 예를 들어 미션을 사용하지 않는 전시회에는 미션 메뉴와 미션 응모 조건이 남지 않아야 한다. 기능을 끄더라도 기존 기록을 즉시 삭제하지 않는다.

### C. 새 행사도 청소년박람회 기본 표현을 물려받음

별도 ‘지역 문화 전시회’를 생성했을 때 이름은 바뀌지만 기본 배경은 `/assets/youth-hero.png`이고 홈에는 ‘박람회는 어떠셨나요?’ 문구가 남았다. 기본 지도 중심·용어·빈 프로그램 영역도 행사에 맞게 설정해야 한다.

제안: 중립적인 기본 테마, 행사명·용어·장소·연락처 설정, 행사 유형별 초기값을 제공한다. 플랫폼 브랜드, 행사 주최 측 브랜드, 참가자에게 보이는 행사명을 분리한다.

### D. 설정된 기능과 실제 행사 준비가 구분되지 않음

지도 코드가 있어도 공개 샘플에는 평면도·경로가 없다. 날씨 코드가 있어도 공개 배포에는 키와 지역 설정이 없고, 안전 연락처도 비어 있다.

제안: ‘코드 있음’ 대신 행사별 ‘준비됨/입력 필요/사용 안 함’으로 관리한다. 공개 전에 행사명·일정·부스 승인·QR·지도·연락처·사용 기능·설문 조건을 확인하는 준비 목록을 둔다.

### E. 다중 행사 지원과 여러 고객사에 제공하는 서비스는 단계가 다름

현재 DB는 행사와 권한을 구분하지만 고객 조직·조직 구성원·이용 계약·조직별 자산 관리 모델은 없다. 한 운영사가 여러 행사를 관리하는 데서 시작할 수 있으나, 독립된 여러 기관이 직접 사용하는 서비스에는 조직 단위 관리가 필요하다.

제안: 플랫폼 운영자 → 주최기관/운영사 → 행사 → 공간·부스·일정·참가 기록의 관계를 설계한다. 고객 셀프서비스를 열기 전에 조직 간 접근 차단과 초대·권한 회수·자료 반출을 검증한다. 처음부터 결제·요금제까지 구현할 필요는 없다.

### F. 데모 배포를 실제 운영 환경으로 바꾸어야 함

현재 `render.yaml`은 무료 테스트용이며 데이터 경로가 `/tmp/festival-demo`이고 자동 배포는 꺼져 있다. 현재 구성 자체가 행사 데이터의 영구 보관을 약속하지 않는다.

제안: 테스트/검토/실운영 환경을 구분하고, 영속 DB·이미지 저장·암호키 보관·백업 복구·배포 버전 확인을 먼저 마련한다. 기술 선택은 부하 목표와 운영 비용을 기준으로 정한다. 다중 고객·복수 서버로 확장할 계획이라면 관리형 PostgreSQL과 별도 이미지 저장소를 우선 검토한다.

## 5. 앞으로의 제품 범위

### 공통 제공 기능

행사 개설·브랜드·일정·공지, 장소·공간·부스 안내, 운영자 권한, 운영 상태, 기본 집계·결과 보고를 중심으로 구성한다.

### 행사별 선택 기능

QR 참여 인증, 미션, 설문·응모·추첨, 현장 문의, 신고 접수, 날씨, 영어 콘텐츠, GPS 경로 안내, 탄소·지역경제 조사 등을 필요에 따라 선택한다. 공통 안내와 비상 연락은 제공하되, 신고 접수와 같은 운영 기능은 담당자가 준비된 행사에서 사용한다.

| 지역 문화·공공 행사 | 장소·시간·현장 안내 | 일정·지도·공지·연락처, QR·미션은 선택 |
| 교육·세미나 행사 | 프로그램과 장소 안내 | 일정·관심 저장·위치·설문, 부스·미션은 선택 |

범용화는 먼저 이처럼 기존 기능으로 설명할 수 있는 유형부터 검증한다. 유료 입장·좌석 예약·대기열·신청 심사가 중심인 행사에는 별도 요구가 있으므로 기존 외부 신청 링크를 활용하고, 수요 확인 후 확장을 판단한다.

예약·좌석·대기열 제외, 부스 단위 고정 QR, 선택 별점, 초기 개인정보 입력 제외, 복구 기능 제외, 실내 통합 평면도 방식은 기존 결정이다. 이번 범용화 요청만으로 이 결정들을 변경하지 않는다.

## 6. 사용자별 기획과 흐름

| 사용자 | 해결할 일 | 기본 흐름 | 성공을 판단할 기준 |
|---|---|---|---|
| 참가자 | 원하는 활동 찾기, 위치 확인, 참여 기록 확인 | 행사 접속 → 일정/부스 탐색 → 위치 안내 → 선택적 QR 참여 → 내 기록 → 선택적 설문 | 안내를 찾아 실제 활동에 도달하고 기록 상태를 이해함 |
| 부스·공간 담당자 | 운영 정보와 실적을 한곳에서 관리 | 등록 → 승인 → QR 준비 → 운영 상태 관리 → 문의·알림 확인 → 종료 실적 | 중복 문의·수기 집계·교대 시 전달 누락 감소 |
| 운영본부 | 준비·당일 문제·마감을 통제 | 행사 설정 → 등록·승인 → 공개 점검 → 현장 대응 → 설문·추첨 마감 → 보고 | 미처리 업무를 놓치지 않고 결과를 일관되게 정리함 |
| 플랫폼 운영자 | 다른 행사에도 재사용 | 고객/행사 관리 → 템플릿 적용 → 담당자 초대 → 운영 점검 → 복제·보관 | 행사별 맞춤 코딩과 반복 설정 감소 |

참가자는 행사를 이용하는 흐름을 보고, 운영자는 업무 진행 상태를 보도록 설계한다. 모든 화면에 같은 기능을 강조할 필요는 없다.

## 7. 화면 개편 방향

### 참가자 화면

- 홈의 상단에서 행사명·오늘 일정·주요 장소·중요 공지를 빠르게 확인하게 한다.
- 키비주얼은 행사별로 유지하되 모바일 첫 화면에서 주요 행동에 접근하기 쉬운 높이와 배치를 검토한다.
- 현재 홈/프로그램/미션/안전/내 참여 구조를 출발점으로 삼고, 사용하지 않는 기능은 메뉴와 홈 카드에서 함께 제외한다.
- 지도는 기존 홈 바로가기 원칙을 유지한다. 행사 유형상 최우선 기능이면 메뉴 위치 변경을 별도로 검토한다.
- 미설정 지도·연락처·날씨를 참가자가 운영자 대신 해결해야 하는 화면으로 만들지 않는다. 운영자에게는 준비 업무를, 참가자에게는 실제 이용 가능한 안내를 제공한다.
- 설문과 추첨은 별도 결과로 설명한다. 미션 없는 행사에서도 설문 이용 조건이 자연스러워야 한다.

### 운영본부 화면

- 준비 중에는 공개 준비 목록, 운영 중에는 미확인 문의·중단 부스·중요 알림, 종료 후에는 설문·지급·보고서를 우선한다.
- 현재 9개 메뉴를 한꺼번에 보여주는 방식에서 권한과 사용 기능에 맞는 업무 화면으로 정리한다. API 권한 검증도 함께 유지한다.
- 최신 화면의 날씨 영역은 대시보드 상단에서 넓은 공간을 차지한다. 야외 행사는 강조하고, 실내 행사나 날씨 미사용 행사에서는 실제 운영 업무를 먼저 보여주는 구성을 권장한다.
- 부스·프로그램이 많은 행사를 위해 표준 CSV 입력과 오류 미리보기·수정 흐름을 검토한다. 현재 일괄 입력이 완성되어 있다고 보지 않는다.

### 결과 보고

행사 개요 → 인증 참여 → 공간·부스 실적 → 프로그램/설문 결과 → 운영 문의 → 운영진 실적 → 개선점의 순서로 종료 보고서를 제안한다. 프로그램의 실제 참석은 별도 측정하지 않으므로 일정 조회·관심 저장·부스 인증을 프로그램 참석으로 바꾸어 표시하지 않는다.

고유 패스 수는 실제 사람 수를 인증한 값이 아니다. 부스 합계는 중복을 포함하고, 실제 방문객·동시 체류·혼잡도는 별도 근거가 필요하다. 지역 지출은 응답자의 신고 합계이며 전체 경제효과가 아니다.

## 8. 개발 순서와 완료 기준

| 단계 | 주요 작업 | 완료 기준 |
|---|---|---|
| 1. 공통 플랫폼의 기반 수정 | 다중 행사 패스 오류, 기능 선택 저장·화면·API 연결, 중립 기본 테마·용어, 행사별 설정 | 같은 기기로 A→B→A 참여가 유지됨. 미션 없는 행사에서 관련 메뉴·조건이 사라짐. 새 행사에 청소년 전용 표현이 남지 않음 |
| 2. 행사 준비·운영 흐름 완성 | 개설 안내, 준비 목록, 권한별 메뉴, 상태별 대시보드, 데이터 입력·검토 | 운영자가 도움 없이 검토용 행사를 만들고 부스 등록→승인→QR 준비→공지→종료 보고를 수행 |
| 3. 실제 운영 기반 구축 | 영속 데이터·이미지·키, 백업 복구, 환경 분리·버전 관리, 외부 API, 부하·현장 검증 | 재시작/배포 후 기록 유지, 별도 환경에서 복구 성공, 정한 접속/인증 목표 충족, 현장 QR·지도·통신 확인 |
| 4. 서로 다른 행사에서 검증 | 박람회와 다른 유형 행사에 적용, 참가자·담당자 사용성 확인, 결과 보고 | 행사별 코드 수정 없이 설정으로 적용하고, 오류·설정 시간·문의·집계 일치 여부를 기록 |
| 5. 반복 제공·자동화 | 조직 관리 강화, 템플릿 관리, 보고서 고도화, 상품권·메시지 자동화 | 반복 수요와 운영 비용을 확인한 기능부터 도입 |

단계 1~2의 화면 개발과 단계 3의 운영 환경 설계는 일부 병행할 수 있다. 실제 참가자 데이터를 받는 운영은 단계 3의 기준을 충족한 뒤 시작한다. 날짜·인력·예산이 정해지지 않았으므로 소요 기간을 확정하지 않는다.

**바로 다음 개발 묶음 제안:** 다중 행사 패스 오류 수정 → 행사별 기능 설정 → 중립 테마·문구 → 행사 설정 안내 → 박람회/지역행사/세미나 검토용 예시 구성. 기존 기능 전체를 다시 만드는 방식은 필요하지 않다.

## 9. 운영 검증과 측정

- 행사 개설·공개 준비에 걸린 시간, 운영자 도움 요청 횟수, 수정이 필요한 설정 수.
- QR 인증 성공·실패·재시도 비율. 중복 요청과 실제 실패를 구분한다.
- 고유 인증 패스, 부스별 고유 패스, 부스 합계의 정의와 원자료 일치.
- 미확인 문의 수, 접수부터 확인·완료까지 걸린 시간.
- 설문 대상·제출·응모 가능·유효 응모를 서로 구분한 수치.
- 결과 보고서를 만들 때 필요한 수기 작업과 누락 항목.
- 합의한 동시 활성 사용자·요청량에서의 응답 지연과 오류, 백업 복구 시간.

목표치는 검토용 행사 운영 결과와 첫 실제 행사 규모를 보고 정한다. 1만 명 현장 체류를 1만 명 앱 동시 접속으로 대체하지 않는다.

## 10. 브랜드와 제공 방식 제안

제품명은 아직 확정하지 않는다. 다양한 행사를 포괄한다는 방향에서는 플랫폼 이름을 특정 연령이나 행사 유형에 묶지 않는 편이 적합하다. 앞서 논의한 Grow Youth는 청소년 행사 템플릿·특화 서비스의 브랜드 후보로 남길 수 있다.

초기에는 운영사가 행사별 설정과 현장 지원을 제공하면서 공통 기능을 검증하는 방식을 권장한다. 독립 고객들이 직접 가입·개설·계약하는 서비스로 확대할 때 조직 관리·요금제·정산을 별도로 설계한다. 현재 코드에 이런 상용 서비스 체계가 완성되어 있다는 의미는 아니다.
